# C60 对照中的 MC 接受尺度与下一项实现边界

## 为什么这项优先于继续调内层参数

目标仍是独立 ASE SSW/LS-SSW，并用随机 C60 与真实 LASP 的同势面对照验收。
复查发现，已恢复的 `native_mc.py` 尚未接入 `paper_reference.run_ssw`。
之前两边都填 150 K，但选择压力并不相同；这不是新发现一段原指令，而是发现已有恢复结果未纳入当前对照解释。

原版已恢复函数在未触发 NSAME 升温时使用

`p = exp[-(Enew-Eold)*96485/(20*8.314*T)]`。

Python 主驱动使用 `exp[-(Enew-Eold)/(ase.units.kB*T)]`。
因此在普通 Metropolis 中取 `T=20*8.314*150/(96485*ase.units.kB)=2999.844423801854 K`
才能匹配原版输入 150 K 的这个指数。它是搜索参数的换算，不是给结构赋予实际热力学温度。
原版无条件消耗随机数、NSAME 状态升温和外层覆盖规则仍是独立差异，不能靠温度换算宣称完整 MC 复现。
依据：[原指令 MC 契约](native-mc-contract.md)，以及当前主驱动 `paper_reference.py` 的真实落点选择分支。

重新运行 `PAMSSW_NATIVE_MC_ELF=.../GA-SSW_program/lasp python -m pytest tests/standalone/test_native_mc.py -q`：
11 passed，包含原机器码的 224 项差分对照。这是算术/状态语义证据，不是搜索有效性证明。

## 不应实现的回退

原版 `climb_` 的 work2/tene0 是每次优化器反向通信调用前的输入快照；Gaussian 中心是另一个状态。
反向通信优化器可能返回等待下一次 E/F 的新试探点，因此恢复输入具有明确的状态一致性作用。
不能把整个 Python bias-quench 的入口或 Gaussian 中心冒充每次原版 dispatch 的入口，
否则会丢弃这一阶段已经完成的优化进展。当前 evaluated-point monitor 保留已评估坐标；
没有证据支持额外退回 Gaussian 中心。严格完整调用链等价仍未建立。
参见 [LBFGS 反向通信](2026-09-12-fixed-lbfgs-rc-lifecycle.md) 和
[快照恢复证据](native-release-snapshot-followup.md)。不为这个未经支持的回退改公共 API。

## 预算的解释边界

原上传 LS-SSW SI §7.3/7.4 的 C60 配置为 50000 **SSW 外步**；GA-SSW 上传全文 Table 1 的
C60 SSW 成功轨迹平均为 10807 外步。它们不是 E/F 调用数，也不是当前 OMAT 势面上的所需预算预测。
本地原始对照只有个位数至数十个完成的外步，因此“未形成 C60 笼”尚不足以否定搜索机制。
继续把每个 6000 E/F 的诊断称为 C60 最终验收会造成目标错位。短对照仅用于定位实现和公平性缺口；
正式验收需要按已测成本规划更长、固定协议且不继续调参的搜索，明确计入两种方法不同的每步成本。

与 `GA-SSW-user.txt`。不将不同模型的论文成功率直接移植到 OMAT。

## 实际结果：本轮未达到温度效应的可归因条件

两个作业均 COMPLETED/0:0，分别 2:51、2:30。四条各 6000 搜索请求，合计 24000 加 26 次新鲜复核，
26/26 返回帧数值合格；两条 C60 仍无笼/参考能量成功。预算截断完整保留为 request_cap。
最佳 E 分别为 C60/17093 -481.794319、C60/17094 -475.536656、Cu55 -173.978594、水15 -218.809946 eV。
**不能据这些终值判断升温好坏**：预注册的“首次 MC 决策差异前轨迹一致”条件未满足。

`prefix-audit.json` 直接比较了旧 strict 与新配置的第一个外步：
输入位置、初始方向完全相同；初始力最大差为 1.22e-14、1.63e-14、2.44e-15、2.00e-15 eV/Å。
但尚未消费第一次 MC 温度时，首个真实落点已分别不同约 0.000196、0.262233、0.001506、0.505443 eV。
温度在核心代码中只用于落点之后的接受分支。因此该首步差异不是 MC 温度造成的。

当前解释是模型/浮点执行路径差异经搜索数值过程放大；已观察到力差与轨迹分叉，尚未把具体 GPU 算子
定位为唯一原因，也没有证明 Safe-total、旋转或势本身哪一个环节负责放大。
PyTorch 官方明确指出随机种子并不保证所有平台/算法的逐位复现，确定性选项也需逐算子核查：
[Reproducibility](https://docs.pytorch.org/docs/stable/notes/randomness.html)。这是诊断依据，不是本任务根因证明。

下一项最小区分检查是相同原始 E/F 账本的首步离线重放，而不是再开一组温度或优化器参数扫描。
旧研究结果仍可描述实际观察到的轨迹与成本；单种子终值变化不能单独当作机制因果证据。
这不撤销能量/力/数组所有权的检查，也不证明所有历史算法结论错误；撤销的是未经验证的严格配对轨迹解释。

## 原版外层覆盖检查的边界

`make_decision` 在 MC 返回后，仅当 `mdinterface==0` 且 `md_force_accept` 为真才覆盖接受位
（0x5d1965–0x5d1984），随后把 mdinterface 置为 -9999（0x5d199e）。
`ssw_move` 中置 0 的分支由 `sswsteps<=1` 或 `nsswstep==0 && lssw_iniopt` 等入口控制
（0x5bd494–0x5bd4d4）；另有 mdinterface==-1 入口。不能仅因 allkeys 中 md_force_accept=T
就认定普通第 9 步走了强制接受。本次独立审查曾作此过强推断，root 查出 -9999 重置及初始化门控后不予采用。
实际两个进程都存在拒绝记录；逐事件 mdinterface 和随机数未记录，仍不对单次接受作唯一机制归因。
allkeys 记录 maxtrap=99999、energy_tol=.1 eV；这些是原运行配置，不是新引入的 Python 默认。

离线脚本 `research/ga_ssw/analyze_c60_mc_semantics.py` 生成
`c60-mc-semantics-20260918/analysis-v2.json`；v1 保留，其中普通 MC 曾错误使用原版近似 R/F 常数，
v2 已改为真实主驱动的 ASE kB。38 行 Minimum found 含 2 个初始化，实际后续候选为 36，
其中 11 个升能、2 个记录接受；一个只有约 1.8e-5 eV，不能把它描述成有意义的跨障碍证据。
另一个 +1.318598 eV 的普通 150 K 概率约 4.98e-45，原版未升温指数约 .00609。
这些是相同能量差下的条件概率，不是重建出来的随机决策或完整轨迹反事实。

## 固定 E/F 重放结果与决策

`replay_mc_first_move.py` 在相同冻结源码及原实验单线程环境下，按顺序读取旧 strict 的 E/F 账本；
每次查询必须与记录位置相差不超过 1e-10 Å，组分、晶胞、PBC 一致，否则失败，不放宽容差。
对两个 C60 起点分别用 150 和 2999.8444238 K 重放第一个外步，四条均完成：

| 起点 | 含初始化请求 | 两个温度的落点 E (eV) |
|---|---:|---:|
| C60/17093 | 134 | -467.4447799764669 |
| C60/17094 | 626 | -469.0101813648187 |

两种温度的首步结果相同，能量与父运行首步严格相同；root 独立检查了这些等式。
证据：`mc-scale-matched-20260918/replay-first-move-v3.json`。这是已有真实 E/F 的代码重放，不新增模型调用，
不代替新轨迹的物理验证，也不说明后续 MC 温度不重要。

失败记录：初版未复现且错误地把已通过的查询标签当作总体通过；其原始 JSON 被子任务误删除，
