## Findings

### eOn: reuse local transition events and parallelize independent saddle searches

The official [eOn API documentation](https://eondocs.org/apidocs/eon) points to the current TheochemUI repository. Its aKMC workflow parallelizes distinct minimum-mode saddle searches from the current state; each successful search also relaxes both sides, determines connected minima, and computes a harmonic TST prefactor. The server then puts the resulting processes in a rate table and samples one transition stochastically. See [`akmc.md` lines 36–60](https://github.com/TheochemUI/eOn/blob/9f8ef20e64ad5074b732a4d9331460fac49d5796/docs/source/user_guide/akmc.md#L36-L60) and [`communicator.md` lines 10–16, 37–53](https://github.com/TheochemUI/eOn/blob/9f8ef20e64ad5074b732a4d9331460fac49d5796/docs/source/user_guide/communicator.md#L10-L53).

Its kinetic database stores a local transition motif (moving atoms plus their neighborhood), strips the rest of the system, and can propose a saddle and mode when a later state has a closely matching local environment. The documented hydrogen-transfer example is a saddle-search seed, not a reusable minimum-energy answer; the database is provided through the separate `tsase` library. See [`kdb.md` lines 10–23, 34–37](https://github.com/TheochemUI/eOn/blob/9f8ef20e64ad5074b732a4d9331460fac49d5796/docs/source/user_guide/kdb.md#L10-L37).

For larger systems, eOn also supports a dynamic script to choose displacement epicenters per new AKMC state, with a neighborhood radius; the selected atoms are cached for searches in that state. This targets likely reactive regions rather than uniformly sampling all atoms. See the official [targeted-displacement tutorial](https://github.com/TheochemUI/eOn/blob/9f8ef20e64ad5074b732a4d9331460fac49d5796/docs/source/tutorials/displacement_scripts.md).

**Transfer boundary:** these are event-discovery and kinetic-completeness tools. They do not directly accelerate a sequential SSW trajectory whose current iterate determines the next step, and event reuse requires transition-state equivalence plus local-environment matching, not merely similar minima. The relevant SSW idea is narrower: if existing defect evidence identifies a small set of repeatedly active regions, spatially target some proposals there while preserving an exploration control. This would be a new proposal policy and needs a matched ablation; it should not be presented as adopting eOn's event database. Independent saddle jobs can be parallelized only when the goal is to enumerate multiple events from the same minimum.

### GOFEE: uncertainty-aware surrogate relaxations screen a parallel candidate pool

The original GOFEE source describes a population of `Ncandidates` newly generated structures each iteration. It relaxes those structures in a Gaussian-process lower-confidence bound (LCB) potential, `E_pred - kappa * sigma`, then selects the most promising candidate for an expensive true-potential evaluation. The implementation distributes candidate generation and surrogate relaxations over MPI ranks, while maintaining one shared search history. See [`gofee.py` lines 71–101](https://gitlab.au.dk/au480665/gofee/-/blob/b6bb43e4b3c363de6fe05b36bceb7aa989c43fb5/gofee/gofee.py#L71-101), [`lines 287–316`](https://gitlab.au.dk/au480665/gofee/-/blob/b6bb43e4b3c363de6fe05b36bceb7aa989c43fb5/gofee/gofee.py#L287-316), [`lines 360–387, 396–429`](https://gitlab.au.dk/au480665/gofee/-/blob/b6bb43e4b3c363de6fe05b36bceb7aa989c43fb5/gofee/gofee.py#L360-429), [`lines 460–470`](https://gitlab.au.dk/au480665/gofee/-/blob/b6bb43e4b3c363de6fe05bceb7aa989c43fb5/gofee/gofee.py#L460-470), and [`parallel_utils.py` lines 3–27](https://gitlab.au.dk/au480665/gofee/-/blob/b6bb43e4b3c363de6fe05b36bceb7aa989c43fb5/gofee/parallel_utils.py#L3-27). Its constrained surrogate relaxer limits displacement from the candidate start and checks position and bond-length constraints ([`bfgslinesearch_constrained.py` lines 60–120](https://gitlab.au.dk/au480665/gofee/-/blob/b6bb43e4b3c363de6fe05b36bceb7aa989c43fb5/gofee/bfgslinesearch_constrained.py#L60-120)).

The implementation has a relatively high speculative budget: default `Ncandidates=30`, up to 200 surrogate relaxation steps per candidate, and normally one selected true evaluation (plus an optional force-directed “dual point”). It filters very high predicted uncertainty, combines the new candidates with the surrogate-relaxed existing population for selection, and trains the surrogate every iteration while hyperparameter optimization is less frequent after the early iterations. These costs and modeling assumptions matter when the target is an already-running ASE SSW walker.

**Transfer boundary:** GOFEE's useful mechanism is pre-oracle ranking of an independent proposal pool, not replacement of the physical SSW update rule. A modest, bounded pool could amortize expensive model work only if generating several proposals does not require advancing the walker and if total proposal, surrogate training, surrogate relaxation, and paid-oracle costs are charged together. Its GP descriptor, uncertainty model, LCB, and population-based mutation are not drop-in components for the current SSW state/history. It is the strongest candidate for a future algorithmic study, but not a small local code absorption.

### HASGO: population search with batched, dynamically active MACE relaxations

HASGO's selected global optimizer is a developed Harmony Search variant. Each new candidate starts from the current global-best vector with coordinatewise memory consideration and pitch adjustment, with a damped fret width; then new and old agents are merged and truncated by fitness. See [`HS.py` lines 11–25, 46–79, 81–127](https://github.com/Fil-end/HASGO/blob/5ba3522dd0f90725a2b005188e21721b6360f0e4/hasgo/mealpy/music_based/HS.py#L11-L127). This is a population metaheuristic over Cartesian coordinates, not an event- or force-guided SSW direction.

Its most concrete efficiency mechanism is `BatchRelaxer`: maintain one ASE optimizer per candidate, build a combined MACE graph batch from all active geometries, evaluate energies/forces in one model call, assign the results back to each optimizer, and drop converged candidates while continuing the remaining ones. The caller enables this only for MACE and sends each candidate generation to the batch relaxer; the default call uses LBFGS, `fmax=0.1`, and an edge-count limit. See [`problems.py` lines 121–143](https://github.com/Fil-end/HASGO/blob/5ba3522dd0f90725a2b005188e21721b6360f0e4/hasgo/hasgo/problems.py#L121-143), [`lines 270–321`](https://github.com/Fil-end/HASGO/blob/5ba3522dd0f90725a2b005188e21721b6360f0e4/hasgo/hasgo/problems.py#L270-321), and [`batch_relaxer.py` lines 41–73](https://github.com/Fil-end/HASGO/blob/5ba3522dd0f90725a2b005188e21721b6360f0e4/hasgo/hasgo/batch_relaxer.py#L41-73), [`119–149`](https://github.com/Fil-end/HASGO/blob/5ba3522dd0f90725a2b005188e21721b6360f0e4/hasgo/hasgo/batch_relaxer.py#L119-149), [`151–220`](https://github.com/Fil-end/HASGO/blob/5ba3522dd0f90725a2b005188e21721b6360f0e4/hasgo/hasgo/batch_relaxer.py#L151-220), and [`264–365`](https://github.com/Fil-end/HASGO/blob/5ba3522dd0f90725a2b005188e21721b6360f0e4/hasgo/hasgo/batch_relaxer.py#L264-365).

**Transfer boundary:** this is batching across independent candidate relaxations, not batching dependent steps of one trajectory. `RelaxBatch.step` attaches a `SinglePointCalculator` with the batched energy/forces and calls `opt.step()` once for each active candidate; that request model fits force-driven one-step optimizers such as its configured LBFGS/FIRE path. It is not a drop-in for Safe-total or ASE `LBFGSLineSearch`, which need to service extra trial-geometry energy/force requests during a step. Also, `max_n_steps` turns off the active flag in the same branch as convergence (lines 216–222); the returned list therefore includes step-limited, potentially unconverged structures. In the HASGO caller, those structures are rescored with the true calculator, but its force rejection uses `np.max(atoms.get_forces()) > 0.2` (lines 310–320), which is a signed component maximum rather than a maximum absolute component or per-atom force norm. That check is not a rigorous force-convergence certificate. The batching pattern is relevant only to an ASE/MACE backend exposing compatible graph/model operations; it does not imply speedup for arbitrary ASE calculators or CPU-only potentials. Reuse the general pattern (active optimizer set + batched model inference + per-candidate state) only after PAM-SSW services the optimizer's actual evaluation requests and validates every returned structure independently; do not import the Harmony Search proposal semantics as an SSW improvement.

## Priority for ASE SSW efficiency

1. **Near-term, implementation-level:** preserve the independent-candidate batching pattern from HASGO only where existing PAM-SSW already creates independent relaxations on a compatible MACE backend. Measure end-to-end paid calls and wall time; a fused model forward is not itself a workflow speedup.
2. **Research-level:** use GOFEE as the nearest structural-search analogue for uncertainty-aware screening of a bounded proposal pool. Any test must charge model fitting and all speculative candidate work and retain the original paid ASE oracle as authority.
3. **Conditional/local:** use eOn's dynamic region targeting only when a defect-locality signal is established independently of the outcome. Its KDB is for repeated transition events and is not a justified cache for ordinary SSW minima.

No component is recommended for immediate core integration by this source review alone. The clones' exact revisions and code paths are now available for focused follow-up, but licenses for GOFEE and HASGO remain unverified.
